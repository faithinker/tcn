## [2026-10-25]

### Fix

- Made `POST /api/account/withdraw` answer `401 unauthorized` when the session snapshot is stale (a password change or an earlier withdrawal in another tab). The `account_events` trigger aborts the batch when the UPDATE matches no row, and nothing caught that, so the request returned an HTML 500; `withdrawAccount` now maps `account_change_conflict` to the same `AccountError` the zero-row path used. `test:account:d1` checks it on workerd D1. (Branch: `feat/roles-phase1-foundation`) - Implemented by Claude
- Made the mail rate limit judge the IP before the mailbox. A request refused by its own IP limit used to spend the target mailbox's slot and 60-second cooldown first, so an attacker whose IP was used up could still make a victim's signup or reset request answer 429 for up to an hour. (Branch: `feat/roles-phase1-foundation`) - Implemented by Claude
- Bounded request bodies while they stream. The new `readBytesWithLimit` (shared with `readJsonWithLimit`) stops reading at the limit, so a body without `Content-Length` can no longer be buffered whole. `POST /api/auth/login` now caps its JSON and form bodies at 8 KiB before the Turnstile check and answers `413 payload_too_large`, and the signup, reset and account routes (`readAccountBody`) use the same reader for their 8 KiB limit instead of reading the whole text first. (Branch: `feat/roles-phase1-foundation`) - Implemented by Claude
- Made `scripts/create-user.mjs` refuse a `--display` or `--role` with no value or with another flag as its value. `--display --remote` used to take `--remote` as the name and create the account in the local database. (Branch: `feat/roles-phase1-foundation`) - Implemented by Claude
- Stopped sign-out from deleting the trusted-device cookie (`tcn_device`). `POST /api/auth/logout` now clears only the session and signup cookies, while a password change, a withdrawal, a password reset and an ended session still clear all three. Sign-out used to delete the cookie that lets a browser skip the account lock, so an attacker could lock out an administrator who had signed out, which undid the lock escalation added with the trusted-device cookie. (Branch: `feat/roles-phase1-foundation`) - Implemented by Claude
- Limited forum writes. One account may post or edit six times in 10 minutes and 40 times a day (a pending account three and 10), answered with `429 rate_limited` and `Retry-After`, through the Q&A limiter table under a `forum:<user id>` key; forbidden requests and hides are not counted. Forum request bodies are now read through `readJsonWithLimit` (64 KiB for a post, 4 KiB for a hide) and answer `413 payload_too_large`, and a forum list page past the last page no longer runs the offset query. The editor shows a message for both errors. Before this a pending account could post to the assembly board without limit, which could spend the D1 Free write allowance. (Branch: `feat/roles-phase1-foundation`) - Implemented by Claude
- Deleted expired email challenges in the daily purge. `auth_email_challenges` rows hold the email address of a signup or password-reset request and used to go only when someone asked for another mail, so an abandoned request kept the address on a quiet site. `purgeExpiredLogs` now deletes them with the other expired rows in the same batch and reports `emailChallenges`; `test:users:d1` checks it on workerd D1. (Branch: `feat/roles-phase1-foundation`) - Implemented by Claude
- Corrected the privacy policy where it disagreed with the code. The email address stays in the verification record until it expires and the daily purge removes it (it said the address was not stored after sending); the bot-check record is a token fingerprint and time kept only for Q&A replay protection (it said a pass/fail result); sign-in and access logs, with the account number and IP address, outlive a withdrawal for their retention periods; CSRF tokens apply to signed-in requests and only the origin check to requests made before sign-in. The signup and profile pages now say that entering the optional affiliation is the agreement the policy relies on; tracker item A12 asks for a legal check of that wording. (Branch: `feat/roles-phase1-foundation`) - Implemented by Claude
- Limited a password reset to three requests per mailbox per day (signup keeps five per hour) and logged a `mail_budget_refused` event when a send is refused for budget. A reset only sends to an existing member, so one known member address at five requests an hour could spend the shared daily mail budget in about 17 hours and leave signup and later resets answering 503 until UTC midnight; it now takes at least 29 distinct member addresses. The limiter's window is now a per-purpose setting, and the event carries the category and the period, never the address. (Branch: `feat/roles-phase1-foundation`) - Implemented by Claude
- Made the password re-authentication cap hold against parallel guesses. `reauthenticate` counted a guess only after the password check had finished, so a burst of requests carrying one stolen session and CSRF token could all be checked before the fifth failure ended the session (twelve of twelve reached the check in the new test). The attempt is now reserved with a conditional upsert before the check and a correct password still clears it, so at most five guesses are checked and the session then ends once; `test:account:d1` checks the burst on workerd D1. The sign-in lock keeps its read-then-record order: each attempt needs its own Turnstile solve and the Cloudflare rate-limit rule caps bursts per IP. (Branch: `feat/roles-phase1-foundation`) - Implemented by Claude
- Stopped a stranger from cancelling a signup that has already proved its mailbox. Asking for a code deleted every signup challenge for that address, so anyone who passed Turnstile (five requests an hour per address) could kill a verified challenge before its owner finished the form. The delete now touches only unverified challenges: a verified one lives until it expires, and finishing still needs the browser's proof cookie and a free address. (Branch: `feat/roles-phase1-foundation`) - Implemented by Claude
- Stopped the password-change and withdrawal notice mails from holding up the answer. The route awaited the notice, and a slow mail provider could keep an already committed change waiting for up to about 20 seconds (two attempts with a 10-second timeout each) before cookies were cleared. `handleAccountMutation` now hands the route a `background` function that registers the notice with `waitUntil` when the runtime has one and otherwise runs it to completion first; the notice already swallowed its own failures, so a failed mail still never fails the request. (Branch: `feat/roles-phase1-foundation`) - Implemented by Claude
- Rejected email addresses written with display-name or list syntax. The address check accepted `<`, `>`, `"`, `,`, `;`, parentheses, brackets, a backslash and control characters, so `evil<victim@x.com>` could become an account name while the mail provider might deliver to `victim@x.com`. The check still takes any single plain address, including non-ASCII ones; `policy.test.ts` pins both lists. (Branch: `feat/roles-phase1-foundation`) - Implemented by Claude

## [2026-10-24]

### Feature

- Added a sign-in log. Each successful sign-in, failed sign-in, new lock and sign-out writes one `auth_events` row (account id, time, `cf-connecting-ip` as received, and a `staff` flag read from the database: 1 for an approved officer). A failed attempt on an unknown username is stored without an account id and the typed username is never stored; attempts turned away by an existing lock or by Turnstile write nothing, so an attack cannot fill the table. A failed write logs `{"event":"auth_log_failed"}`; for an approved officer a failed `login_success` write is retried once with the same id (a duplicate id is ignored, so a commit whose answer was lost does not write twice) and, if the retry fails too, answers `503 auth_log_unavailable` with no session and does not count as a wrong password, so an officer never gets in without a record, while every other account signs in regardless. Migration `0013_auth_events.sql` adds triggers that reject any `UPDATE` and any `DELETE` younger than 395 days for staff rows or 90 days for the rest, and every recorded event deletes the expired rows of both classes. Tests cover the module, the triggers, the login and logout routes and a real workerd D1 (`test:users:d1`). (Branch: `feat/roles-phase1-foundation`) - Implemented by Claude
- Gave accounts that are not approved officers a more lenient failed-sign-in limit: ten failures in 15 minutes instead of five. An unknown username uses the lenient limit too, so the moment of the lock does not reveal who is registered; an IP row is judged by the class of the account being tried. Officer accounts, the escalating lock steps and the ten-attempt trusted-device limit are unchanged. (Branch: `feat/roles-phase1-foundation`) - Implemented by Claude
- Added a daily scheduled purge of expired logs. A Cron Trigger (`17 18 * * *`, 03:17 KST) runs `purgeExpiredLogs`, which deletes `admin_access_events` older than 395 days, `auth_events` older than 395 days (staff) or 90 days (others) and clears `user_audit_events.ip` older than 395 days in one batch, so expired rows go even when nobody signs in or opens `/admin/users`. The SQL is shared with the existing write-time purge, and a batch that a delete guard rejects rolls back whole and logs `log_retention_failed`. The Worker entry is now `src/worker.ts` (`main` in `wrangler.jsonc`), which serves requests through `@astrojs/cloudflare/handler` and adds the `scheduled` handler. Tests cover the purge, the handler and the real workerd D1; a local `wrangler dev --test-scheduled` call deleted exactly the expired rows. (Branch: `feat/roles-phase1-foundation`) - Implemented by Claude
