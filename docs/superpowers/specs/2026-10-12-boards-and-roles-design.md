**2026-10-14 개정:** 가입 승인·반려와 다른 사람의 게시판 글 숨김을 임원 전체가 아니라 회장과 부회장(결정권자)에게만 부여한다. 승인 전 계정을 "준회원"이라 부르고, 준회원도 총회 게시판을 열람·작성할 수 있게 한다. 등급은 비로그인 < 준회원 < 회원 < 이사진 < 회장·부회장 순서이고, 상위 등급은 하위 등급이 쓸 수 있는 기능을 모두 쓸 수 있다. 변경은 D1, D3~D5, D8, D9, D11, D12와 4~17장에 반영했다.

**2026-10-20 개정:** 감사·고문은 승인된 회원에 임원 게시판 특별 접근을 추가한다. 결정권자는 일반 계정의 권한을 관리하지만 자기 자신과 기존 결정권자의 상태·역할·결정권·특별 접근을 변경할 수 없다. 신규 결정권자도 동일하게 보호한다. Forum·계정·사용자 관리 구현은 [통합 Phase 2 계획](../plans/2026-10-20-forum-and-user-management.md)에 따라 진행하고, 전체 로컬 확인·최종 검증 뒤 한 번에 운영 배포한다. 공개 가입은 별도 통제한다.

**2026-10-21 개정:** 이메일 소유 인증을 후속 절차에서 가입 완료의 필수 선행 절차로 바꿨다. 가입은 이메일 입력, 6자리 코드 인증, 이름·소속·비밀번호 입력, 최종 제출 순서로 진행하고, 최종 제출 때 비로소 준회원 계정을 만든다. 비밀번호 재설정과 본인 탈퇴도 같은 단계에 구현했고, 새 비밀번호 정책은 NFC 정규화 후 15~64자로 바꿨다. 변경은 D6, D10, 7.2, 9.1, 11장, 15~17장에 반영했다. 구현 상세는 [계정 수명주기](../../account-lifecycle.md)와 [`MEMBERSHIP_FLOW.md`](../../../MEMBERSHIP_FLOW.md)를 따른다.

## 1. 요약

TCN 사이트에 두 가지 역할(임원, 회원)과 세 가지 계정 상태(승인 대기, 승인 완료, 반려)를 도입한다. 승인 전 계정은 "준회원", 승인된 계정은 "회원"이라 부른다. 임원은 세미나 글과 Q&A 공식 답변을 관리하고 임원 게시판과 총회 게시판을 사용한다. 임원 중 회장과 부회장만 가입자를 승인하거나 반려하고 다른 사람의 게시판 글을 숨길 수 있다. 준회원과 일반 회원은 총회 게시판을 사용하고, 승인된 감사·고문은 별도 특별 접근으로 임원 게시판도 사용한다. Q&A 질문은 누구나 작성한다. 결정권자는 일반 계정의 역할·결정권·특별 접근을 사용자 관리 화면에서 변경한다. 세미나 게시판과 익명 Q&A는 이미 구현되어 있으므로 새로 만들지 않는다.

작업은 기반 구현과 후속 통합 구현으로 나눈다. 각 작업 중 테스트·타입 검사를 수행하고, 전체 기능 완료 뒤 역할별 로컬 확인·최종 검증·운영 배포를 진행한다.

1. Phase 1: 역할·상태 기반과 권한 가드 교체(구현 완료)
2. Phase 2: 특별 접근 확장, forum 엔진·두 게시판, 계정·가입·사용자 관리(로컬 구현·검증 완료, 운영 반영 대기; [검증 기록](../../phase2-verification.md))
3. 공개 가입 활성화: 개인정보·남용 방어 준비와 별도 승인 후

## 2. 배경

### 2.1 요구사항

- 이사회(Board of Directors)는 임원 회의다. 구성원은 회장, 부회장, 이사다.
- 총회(General Assembly)는 회원 회의다. 구성원은 회원이다. 사이트의 총회 게시판은 가입 직후의 준회원도 이용한다.
- 게시판은 네 종류다.
  - 세미나 게시판: 누구나 열람한다. 이미 있다.
  - 임원 게시판: 승인된 임원과 특별 접근을 받은 감사·고문이 열람·작성한다.
  - 총회 게시판: 준회원, 회원, 임원이 열람한다. 가입이 반려된 계정과 비로그인 사용자는 열람하지 못한다.
  - Q&A 게시판: 익명으로 누구나 질문을 쓸 수 있다. 이미 있다.
- 역할은 임원과 회원 두 가지뿐이다.
- 가입한다고 바로 회원이 되지는 않는다. 가입 직후에는 준회원이고, 회장 또는 부회장이 승인해야 회원이 된다.
- 가입 승인과 다른 사람의 게시판 글 숨김은 임원 중 회장과 부회장만 한다.
- 임원 게시판과 총회 게시판에서 글을 만들고, 고치고, 지울 수 있어야 한다.

### 2.2 현재 상태 (코드 실측)

- 런타임은 Astro 7과 Cloudflare Workers이고 저장소는 D1(`tcn-content`)과 R2(`tcn-media`)다.
- `users` 테이블은 `id`, `username`, `password_hash`, `display_name`, `created_at`, `session_version` 컬럼만 가진다. 역할과 상태 컬럼이 없다.
- 계정은 `scripts/create-user.mjs`로 수동 발급한다. 가입 화면이 없다.
- 인증은 HMAC 서명 쿠키(1일)이고 토큰에는 `uid`, 만료 시각, 세션 버전만 담긴다.
- 인증만 통과하면 누구나 세미나 글 등록·수정, 미디어 업로드, Q&A 공식 답변·공개 전환을 할 수 있다. 이 권한을 `getSessionUid`로 확인하는 비테스트 파일이 15개 있다.
- Q&A 변경 API는 `requireAdminMutation`(`src/lib/qna/security.ts`)으로 세션, 동일 출처, `sec-fetch-site`, CSRF 토큰을 모두 검사한다. CSRF 토큰은 `qna-csrf:<세션 토큰>`의 HMAC이다.
- 운영 배포(`.github/workflows/deploy-workers.yml`)는 D1 Time Travel 북마크를 남기고, 원격 마이그레이션을 적용하고, Worker를 배포하고, `/api/health`와 `/api/ready` 확인에 실패하면 Worker를 롤백한다. 운영 마이그레이션은 기존 Worker와 호환되는 추가 변경만 허용한다(`docs/operations-runbook.md`).
- `IDEA.md`의 범위 경계는 공개 회원가입과 커뮤니티 기능을 제외한다고 정하고 있다. 이 설계는 그 경계를 바꾸므로 14장의 문서 개정이 함께 필요하다.

### 2.3 목표와 비목표

목표는 다음과 같다.

- 임원과 회원 두 역할로 열람·작성 권한을 나눈다.
- 회장 또는 부회장이 승인한 계정만 회원이 되는 가입 절차를 만든다.
- 기존 운영 동작을 1단계 배포에서 바꾸지 않는다.
- 새로 추가되는 경로가 권한 검사를 빠뜨리면 CI가 실패하게 한다.

비목표는 15장(후속 절차)에 따로 모았다.

## 4. 역할·상태·권한 모델

### 4.1 판정 규칙

- 권한은 `status`를 먼저 확인하고, 그다음에 `role`과 `is_executive`를 확인한다. `rejected` 계정은 `role` 값과 관계없이 어떤 보호 기능도 쓸 수 없다. `pending` 계정(준회원)은 `role` 값과 관계없이 총회 게시판과 `/account`만 쓸 수 있다. 임원 권한과 결정권은 `status`가 `approved`인 계정에만 유효하다.
- 결정권은 `status = approved`, `role = officer`, `is_executive = 1`을 모두 만족할 때만 인정한다. 다른 조합에서 `is_executive`가 1이어도 무시한다.
- 로그인 계정의 등급은 준회원(`pending`) < 회원(`approved`, `member`) < 이사진(`officer`, 결정권 없음) < 회장·부회장(`officer`, `is_executive = 1`) 순서로 계산하고, 비로그인 사용자는 이 순서의 맨 아래에 둔다. 상위 등급은 하위 등급이 쓸 수 있는 기능을 모두 열람·작성할 수 있다. 삭제·숨김은 이 규칙의 예외이고 4.2에서 따로 정한다. `rejected`는 이 순서에 넣지 않으며 공개 기능과 `/account`만 쓴다.
- 특별 접근은 `status = approved`, `role = member`, `can_access_directors_forum = 1`일 때 임원 게시판에만 적용한다. 기본 등급은 member로 유지한다. pending/rejected이면 특별 접근을 무시한다.
- 신규 가입과 승인만으로 특별 접근·임원·결정권은 생기지 않는다. 이후 임명·권한 변경이 있으면 가입 시점이 아닌 현재 계정 설정으로 판단한다.
- `pending`과 `rejected` 계정은 로그인할 수 있다. 두 계정 모두 `/account`에서 본인 상태를 확인할 수 있고, `pending` 계정은 총회 게시판도 쓸 수 있다.
- 역할, 상태, 결정권은 세션 토큰에 넣지 않고 요청마다 D1에서 읽는다. 그래서 승인, 반려, 역할·결정권 변경이 즉시 반영되고 세션 버전을 올릴 필요가 없다.

표의 "이사진"은 `role = officer`이고 `is_executive = 0`인 승인 완료 계정(회장·부회장을 제외한 임원)이고, "결정권자"는 `is_executive = 1`인 승인 완료 임원 계정이다. "준회원"은 `pending`, "반려"는 `rejected` 계정이다. 임원 역할이어도 `pending`이거나 `rejected`이면 해당 열의 권한만 갖는다.

게시판 수정·숨김은 현재 해당 게시판 접근 권한을 가진 계정에만 허용한다. 감사·고문은 승인된 member + 특별 접근이며 기본 officer 등급과 구분한다. 사용자 변경은 다음 보호 규칙을 추가 적용한다.

### 4.3 계정 상태 전이

| 전이                    | 동작      | 허용 대상                            |
| ----------------------- | --------- | ------------------------------------ |
| `pending` → `approved`  | 승인      | 결정권자가 일반 회원 계정에 대해서만 |
| `pending` → `rejected`  | 반려      | 결정권자가 일반 회원 계정에 대해서만 |
| `rejected` → `approved` | 반려 복구 | 결정권자가 일반 회원 계정에 대해서만 |

- 승인(`pending` → `approved`)은 준회원을 회원으로 만드는 전이다. 승인 전후에 총회 게시판 접근 범위는 달라지지 않는다.
- 자기 자신과 변경 전 `is_executive = 1`인 대상 계정의 상태·역할·결정권·특별 접근을 바꿀 수 없다. 회장↔부회장 상호 변경과 반려 처리로 권한을 제거하는 우회를 차단한다. 비정상 상태의 결정권자도 보호한다.
- 같은 이메일로 다시 가입하는 것은 `username`의 유일 제약이 막는다. 반려된 사람은 결정권자가 복구해야 한다.
- 승인된 결정권자는 승인된 일반 대상의 역할·결정권·특별 접근을 화면에서 변경할 수 있다. pending/rejected 대상은 먼저 승인·복구해야 한다. 결정권은 officer만, 특별 접근은 member만 허용한다. officer 전환 시 특별 접근은 0으로 명시한다.
- 새로 결정권을 부여받은 대상도 이후 보호된다. 기존 결정권자 해제·교체와 초기 두 결정권자 bootstrap은 별도 운영 절차로 처리한다. 사이트에는 보호 해제 API를 두지 않는다.
- 회원 제명과 승인 취소는 이번 범위에 넣지 않는다. 정관 제6조에서 이사회 의결 사항이다.

## 5. 데이터 모델

마이그레이션은 기존 규칙에 따라 추가만 하고, 번호는 구현 착수 시 최신 마이그레이션 다음 번호를 사용한다. 현재 0008은 적용 대상 기존 기반이며, 0009_forum_access.sql과 0010_user_audit_events.sql을 예약한다. 이미 작성된 0008은 수정하지 않는다.

### 5.1 `users` 컬럼 추가 (`0008`, 1단계)

```sql
alter table users add column role        text    not null default 'member'
  check (role in ('officer', 'member'));
alter table users add column status      text    not null default 'pending'
  check (status in ('pending', 'approved', 'rejected'));
alter table users add column affiliation text;
alter table users add column is_executive integer not null default 0
  check (is_executive in (0, 1));
alter table users add column revision    integer not null default 1 check (revision >= 1);
alter table users add column decided_by  text references users(id);
alter table users add column decided_at  integer;

-- 기존 수동 발급 계정은 지금 모든 권한을 가지고 있으므로 동작을 유지한다.
update users set role = 'officer', status = 'approved';
```

- 기본값은 가장 권한이 낮은 `member`, `pending`, 결정권 없음(`is_executive = 0`)이다. 새 행이 실수로 임원 권한이나 결정권을 갖지 않게 하기 위해서다. 다만 총회 게시판은 `pending` 계정에도 열려 있다(D3).
- `is_executive`는 `role = officer`이고 `status = approved`일 때만 의미를 가진다(4.1). 두 컬럼에 걸친 `check` 제약은 두지 않고, 판정 함수와 운영자 스크립트(10.3)가 이 조건을 지킨다.
- 기존 계정의 `is_executive`는 `0`으로 둔다. 회장·부회장 지정은 10.2에서 한다. 가입 승인과 타인 글 숨김은 통합 2단계에서 구현하고 초기 권한 검증 후 연다.
- `decided_by`와 `decided_at`은 가장 최근 승인·반려 결정을 가리키고, 사용자 관리 화면이 읽는다. 이력은 5.3의 감사 기록이 가진다.
- `decided_at`은 같은 테이블의 `created_at`처럼 유닉스 초 정수다.
- 이메일은 별도 컬럼 없이 `username`에 소문자로 저장한다. 기존 계정의 `username`은 이메일 형식이 아니며, 이메일 형식 검사는 신규 가입에만 적용한다.
- 0008의 기본값·허용 값·FK 제약은 Phase 1 D1 검증으로 확인했다.

### 5.2 특별 접근과 `forum_posts` (`0009`, 통합 2단계)

```sql
alter table users add column can_access_directors_forum integer not null default 0
  check (can_access_directors_forum in (0, 1));
```

기존 계정의 특별 접근도 기본 0이다. 운영 명단 매칭 후 승인된 감사·고문에게만 부여한다.

```sql
create table forum_posts (
  id          text primary key,
  board       text not null check (board in ('directors', 'assembly')),
  title       text not null
                check (length(trim(title)) between 1 and 120)
                check (instr(title, char(0)) = 0),
  body        text not null
                check (length(trim(body)) between 1 and 10000)
                check (instr(body, char(0)) = 0),
  author_id   text not null references users(id),
  revision    integer not null default 1 check (revision >= 1),
  created_at  text not null default (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
  updated_at  text not null default (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
  deleted_at  text,
  deleted_by  text references users(id),
  check ((deleted_at is null) = (deleted_by is null))
);

create index forum_board_created
  on forum_posts (board, deleted_at, created_at desc, id desc);
```

- 시각 컬럼은 같은 계열인 Q&A 테이블의 ISO 텍스트 형식을 따른다.
- 삭제는 실제 삭제가 아니라 `deleted_at`과 `deleted_by`를 채우는 숨김이다.

### 5.3 `user_audit_events` (`0010`, 통합 2단계)

이전 승인 전용 감사 스키마를 확장한다. 아래 계약을 마이그레이션과 실제 D1 테스트에 반영한다.

- 대상/수행자 FK, 동작 approved/rejected/reapproved/permissions_changed.
- 변경 전후 status/role/is_executive/can_access_directors_forum.
- before_revision ≥ 1, after_revision = before_revision + 1.
- 고유 request_id, 요청 내용 비교용 지문, ISO 생성 시각.
- (target_user_id, before_revision) 유일 제약.
- 이메일·비밀번호·세션·CSRF는 기록하지 않는다.
- 사용자 변경은 한 D1 배치에서 조건부 UPDATE 후 감사 INSERT로 처리한다. 감사 INSERT 검증 트리거는 실제 사용자 revision·권한과 after 스냅샷이 다르면 오류를 발생시켜 배치 전체를 취소한다. (대상, before_revision) 유일 제약과 함께 영향 행 0건을 성공/독립 감사로 남기지 못하게 한다. 실제 D1에서 실패·충돌·재시도를 검증한다.
- 동일 수행자·requestId·대상·내용의 재시도는 권한 재검사 후 기존 성공 결과를 반환한다. 다른 내용의 requestId 재사용은 409다.

## 6. 권한 강제 방식

### 6.1 공용 모듈

`src/lib/auth/`에 다음을 추가한다.

- `getSessionUser(request)`: 세션이 유효하면 `id`, `username`, `displayName`, `role`, `status`, `isExecutive`, `canAccessDirectorsForum`을 반환하고, 아니면 `null`을 반환한다. 기존 `getSessionUid`가 이미 사용자 행을 읽으므로 DB 조회 횟수는 늘지 않는다.
- `requireOfficer`, `requireExecutive`, `requireActiveAccount`: 각각 승인된 임원, 결정권자(회장·부회장), 반려되지 않은 로그인 계정(준회원, 회원, 임원)을 요구한다. 페이지용과 API용을 구분한다. 페이지는 비로그인이면 `/login`으로 보내고 권한이 없으면 안내 화면을 보여 준다. API는 비로그인이면 401(`unauthorized`), 권한이 없으면 403(`forbidden`)을 반환한다.
- `canAccess(user, action)`: 4.2의 매트릭스를 그대로 구현한 순수 함수다. 기본 등급과 별개로 승인된 감사·고문의 임원 게시판 특별 접근을 허용한다. 총회는 준회원 이상이다. 게시판 글 수정·삭제는 글 작성자 정보를 함께 받는다.
- `requireMutation(request, { scope, require })`: `requireAdminMutation`을 일반화한 것이다. 세션, 동일 출처, `sec-fetch-site`, CSRF를 모두 검사하고 역할 조건을 추가로 확인한다. `require`는 `'officer'`, `'executive'`, `'activeAccount'` 중 하나다.

### 6.2 CSRF 토큰 호환

CSRF 토큰은 `scope`로 도메인을 분리한다(`qna-csrf:`, `forum-csrf:`, `users-csrf:`). Q&A는 기존 접두사를 그대로 쓰므로 이미 열려 있는 관리 화면의 토큰이 배포 때문에 무효가 되지 않는다. 오류 클래스 이름만 공용 이름으로 바꾸고, 상태 코드와 오류 코드 문자열은 그대로 유지한다.

### 6.3 교체 대상

`getSessionUid`를 쓰는 비테스트 파일 15개의 처리는 다음과 같다.

| 처리                                   | 대상                                                                                                                                                                                                                                                    |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 임원 전용 가드로 교체 (11개)           | `qna/security.ts`(Q&A 답변·공개 전환), `admin/index`, `admin/posts/new`, `admin/posts/[id]`, `admin/questions/index`, `admin/questions/[id]`, `api/posts/index`, `api/posts/[id]`, `api/media/index`, `api/media/[id]`, `api/maintenance/media-cleanup` |
| 세션만 확인하고 가드는 쓰지 않음 (4개) | `api/auth/logout`, `api/auth/me`(응답에 `role`, `status` 추가), `api/questions/index`(익명 질문 허용), `admin/login`(`/login`으로 이동시킴)                                                                                                             |

### 6.4 커버리지 테스트

기존 `*-parity.test.ts` 방식으로 `src/lib/auth/route-guard-coverage.test.ts`를 추가한다. 이 테스트는 `src/pages/admin/**`, `src/pages/api/**`, `src/pages/forum/**`의 모든 경로 파일을 읽어서, 다음 중 하나를 만족하지 않으면 실패한다.

- 공용 가드 함수(`requireOfficer`, `requireExecutive`, `requireActiveAccount`, `requireMutation`)를 호출한다.
- 테스트 파일 안의 명시적 공개 목록에 한 줄 사유와 함께 올라 있다.

공개 목록에는 현재 존재하는 경로만 올린다. 1단계의 목록은 `admin/login`, `api/auth/login`, `api/auth/logout`, `api/auth/me`, `api/health`, `api/ready`, `api/questions/index`다. `api/auth/signup` 같은 경로는 해당 경로가 생기는 단계에서 추가하고, 목록에 있으나 파일이 없는 항목은 테스트가 실패하게 한다. 이 테스트는 호출 문자열의 존재를 확인하는 것이므로 가드가 올바르게 쓰였는지까지 증명하지는 못한다. 올바른 사용은 12장의 매트릭스 테스트와 핸들러 단위 테스트가 보완한다.

### 7.2 가입

- 가입은 두 단계다. 먼저 이메일을 입력하면 6자리 코드를 보내고, 코드를 인증한 뒤에만 이름·소속·비밀번호(확인 입력 포함) 입력란이 열린다. 코드는 10분 뒤 만료되고 챌린지당 5회까지 시도할 수 있다. 인증 상태는 브라우저에 묶여 20분 동안 새로고침해도 유지된다. 인증한 이메일은 바꿀 수 없고, 바꾸면 이전 인증이 폐기된다. 계정은 최종 제출 때 처음 만들어지므로 미인증 계정은 생기지 않는다.
- 입력 항목은 이메일(아이디), 비밀번호, 이름(필수), 소속(선택)이다. 전화번호, 생년월일, 주소는 받지 않는다(`MEMBERSHIP_FLOW.md`의 원칙).
- 이메일은 양끝 공백 제거·소문자 정규화 후 형식과 254자 상한을 검사한다. 비밀번호는 NFC 정규화 후 유니코드 코드포인트 기준 15~64자이고, 공백과 기호를 허용하며 문자 종류의 조합은 요구하지 않는다. 제어·서식·보이지 않는 문자, 단순 반복과 연속, 흔한 단어에 숫자만 덧붙인 형태, 계정 아이디나 이메일 앞부분을 포함한 값은 거부한다. 운영에서는 Pwned Passwords 범위 조회(해시 앞 5자만 전송)로 유출된 비밀번호도 거르고, 이 확인을 할 수 없으면 비밀번호 설정을 거부한다. 이름 1~100자, 소속 200자 이하다. 기존 수동 계정의 username 로그인은 유지한다.
- 저장되는 계정은 `role = member`, `status = pending`, `is_executive = 0`, `can_access_directors_forum = 0`이다. 클라이언트의 권한 필드 주입은 거부한다. 비밀번호 해시는 `hashPassword`를 `normalize: true`로 호출해 `pbkdf2-nfc` 형식으로 저장한다. 기존 `pbkdf2` 해시는 입력 의미를 그대로 유지한다.
- 가입이 끝나면 세션 쿠키를 발급해 자동으로 로그인시키고 `/account`로 보낸다.
- 코드 발송 단계는 이메일의 가입 여부를 확인하지 않고 같은 응답을 준다. 메일 본문이 이미 계정이 있으면 로그인하라고 안내한다. 이미 쓰인 이메일이면 최종 제출에서 `email_taken`(409)을 반환하지만, 이 응답은 코드를 인증해 메일함 소유를 증명한 이메일에만 나온다. 그래서 다른 사람의 가입 여부를 알아내는 데는 쓸 수 없다.

### 7.3 공개 시점 분리

`SIGNUP_ENABLED`는 Workers 변수(`vars`)이고 값이 정확히 `true`일 때만 가입이 열린다. 변수가 없거나 다른 값이면 꺼진 것으로 본다. `/api/ready`의 검사 대상에는 넣지 않는다. 시크릿이 아니고, 꺼진 상태가 정상이기 때문이다. 켜는 일은 설정 변경이므로 변경 이력이 git에 남는다. 개인정보 처리방침과 스팸 방어가 갖춰지기 전에는 켜지 않는다.

### 7.4 로그인과 이동

- 로그인 API(`/api/auth/login`)의 인증 방식과 속도 제한은 그대로 두고, 성공 응답에 `role`과 `status`를 추가한다.
- 로그인 후 이동할 곳은 안전하다고 검증된 `returnTo`가 있으면 그곳이고, 없으면 임원은 `/admin`, 준회원과 회원은 `/forum/assembly`, 반려된 계정은 `/account`다.
- `safeAdminReturnTo`는 `/admin`, `/forum`, `/account` 경로만 허용하도록 넓힌다. 외부 주소와 `//`, 역슬래시를 거부하는 기존 검사는 그대로 유지한다.

### 7.5 헤더와 푸터

`/people`, `/about/*`, `/contact`, `/404`는 프리렌더 페이지이므로 Header가 서버에서 세션을 읽을 수 없다. 로그인 상태에 따른 링크는 클라이언트 스크립트가 `/api/auth/me`를 호출한 뒤 표시한다.

- 임원에게 "Directors Forum", "Assembly Forum", "Account"를 보여 준다.
- 승인된 특별 접근 회원에게 "Directors Forum", "Assembly Forum", "Account"를 보여 주되 운영 관리자 메뉴는 보여 주지 않는다.
- 준회원과 일반 회원에게 "Assembly Forum", "Account"를 보여 준다.
- `/api/auth/me`는 메뉴용 canAccessDirectorsForum capability를 반환한다. raw is_executive·감사 기록은 반환하지 않고, 클라이언트 메뉴와 별도로 서버가 권한을 강제한다.
- 반려된 계정에게 "Account"를 보여 준다.
- 비로그인 사용자에게는 푸터에 정적인 "Sign in" 링크를 둔다. 헤더의 공개 내비게이션은 바꾸지 않는다.

### 7.6 `/account`

이름, 이메일, 소속, 상태를 보여 준다. 상태는 "준회원"(`pending`), "회원"(`approved`), 반려(`rejected`)로 표시한다. 준회원이면 회장 또는 부회장이 검토 중이라고 안내하고 총회 게시판 링크를 보여 준다. 반려이면 승인되지 않았다는 사실과 사무국 연락처(`content.ts`의 기존 값)를 안내한다. 회원이면 총회 게시판 링크를 보여 준다. 화면 문구는 영어이고 `src/i18n`에 둔다.

## 8. Forum

### 8.1 이름과 경로

영어 UI에서 `board`는 이사회(Board of Directors)와 혼동되므로 사이트 안에서 게시판을 `forum`이라고 부른다. 화면 이름은 "Directors Forum"과 "Assembly Forum"이다.

| 경로                                  | 용도                             |
| ------------------------------------- | -------------------------------- |
| `/forum/directors`, `/forum/assembly` | 목록 (한 페이지 20건, 최신순)    |
| `/forum/[board]/new`                  | 글쓰기                           |
| `/forum/[board]/[id]`                 | 상세. 수정·삭제 조작을 포함한다. |
| `POST /api/forum/[board]`             | 글 생성                          |
| `PUT /api/forum/[board]/[id]`         | 글 수정 (`expectedRevision`)     |
| `DELETE /api/forum/[board]/[id]`      | 글 숨김 (`expectedRevision`)     |

### 8.2 게시판별 허용 역할

게시판 종류는 코드의 상수로 고정한다. 기본 등급과 추가 특별 접근을 함께 판정한다. 반려 계정은 어느 게시판도 쓸 수 없고, 준회원의 특별 접근 플래그는 무시한다.

| 게시판      | 열람                                   | 작성                                   |
| ----------- | -------------------------------------- | -------------------------------------- |
| `directors` | 승인된 임원 또는 승인된 특별 접근 회원 | 승인된 임원 또는 승인된 특별 접근 회원 |
| `assembly`  | 준회원 이상                            | 준회원 이상                            |

### 8.3 동작 규칙

- 본문은 일반 텍스트이고 줄바꿈만 유지한다. 마크다운, HTML, 자동 링크는 쓰지 않는다. 화면에 출력할 때는 항상 이스케이프한다.
- 수정은 작성자 본인만 할 수 있다. 삭제는 작성자 본인과 결정권자(회장·부회장)가 할 수 있다. 삭제된 글은 목록과 상세에서 보이지 않는다.
- `expectedRevision`이 맞지 않으면 409를 반환하고, 화면은 다시 불러오라고 안내한다.
- 작성자 표시는 이름만 쓴다. 이메일은 forum 어디에도 노출하지 않는다. 표시 이름이 없는 기존 계정은 역할 이름("Officer" 또는 "Member")으로 표시한다.
- 반려된 계정이 이전에 쓴 글은 그대로 남고, 결정권자가 글마다 숨긴다.
- 알림(Discord, Telegram)은 보내지 않는다.
- 이번 범위에서 제외한다: 댓글, 첨부 파일, 검색, 상단 고정.

### 8.4 캐시와 색인 방지

모든 forum 응답과 `/admin/users`, `/api/users/**`, `/account`, `/login`, `/signup`, `/api/forum/**`, `/api/auth/me`에 `Cache-Control: no-store`와 `X-Robots-Tag: noindex`를 붙인다. 성공·오류·리다이렉트·릴리스 gate의 503에도 적용한다. 기존 공용 보안 헤더는 유지하고 비공개 경로는 사이트맵에서 제외한다.

### 8.5 화면 톤

`PRODUCT.md`는 "소셜 피드와 커뮤니티 앱"을 반(反)레퍼런스로 정했다. 따라서 카드형 피드가 아니라 제목, 작성자, 날짜를 가진 기록형 목록으로 만든다. 목록은 기존 `PublicPagination`을 재사용한다. 접근성 기준은 WCAG 2.2 AA이며 폼은 레이블과 `role="alert"` 오류 안내를 갖춘다.

## 9. 결정권자용 사용자 관리

### 9.1 화면

`/admin/users`를 추가하고 결정권자에게만 어드민 메뉴의 "Users"를 보여 준다. 이사진 등 다른 임원은 이 화면에 접근할 수 없다(`requireExecutive`, 403). Q&A의 대기 건수 배지(`countAdminQuestions`)와 같은 방식으로 승인 대기(준회원) 건수를 메뉴에 표시한다. 이 배지가 결정권자가 새 가입자를 알아채는 유일한 수단이다.

- 탭: 준회원(승인 대기), 회원(승인 완료), 반려. 쿼리 `?status=`와 `?page=`를 쓰고 기존 `AdminPagination`을 재사용한다.
- 열: 이름, 이메일 또는 기존 username, 소속, 가입일, 역할, 특별 접근, 결정권, 결정한 결정권자와 결정 시각(승인 완료·반려 탭).
- 정렬: 승인 대기는 오래된 순, 나머지는 결정 시각의 최신순.
- 새로 가입한 계정의 이메일은 가입 때 코드로 인증을 마쳤다. 인증은 메일함의 소유만 증명하고 신분은 증명하지 않으므로, 결정권자는 이메일이 아니라 이름과 소속을 근거로 판단해야 한다. 이 안내는 행마다 표시하지 않고 목록 위에 문구 한 줄로 알린다. 이전에 수동으로 발급한 계정의 이메일은 인증되지 않은 상태다.

### 9.2 API

- `PATCH /api/users/[id]/status`: status/expectedRevision/requestId. 4.3의 전이만 허용한다.
- `PATCH /api/users/[id]/permissions`: role/isExecutive/canAccessDirectorsForum/expectedRevision/requestId. 승인된 대상의 최종 권한 상태 전체를 지정한다.
- 두 경로 모두 `requireMutation(scope: users, require: executive)`와 최신 대상 보호 검사로 처리한다.
- 자기 자신·변경 전 결정권자는 상태·역할·특별 접근을 포함한 모든 관리 변경이 403이다. 새 결정권자도 이후 보호된다.
- 입력 오류 400, 비로그인 401, 권한 부족 403, 없는 대상 404, 전이·revision·requestId 충돌 409다.
- 수행자의 현재 권한 및 대상 보호 여부를 저장 조건에 포함한다. 수행자 강등·대상 승격과 경합하는 오래된 요청도 제한을 우회하지 못한다.
- 사용자 변경과 감사 기록이 함께 성공하거나 함께 취소되게 한다. 상태 변경만 decided_by/decided_at을 갱신한다.

### 9.3 화면 제한

역할·결정권·특별 접근 변경과 확인 UI를 제공한다. 자기 자신과 기존 결정권자는 읽기 전용으로 표시하고, 결정권을 부여하면 그 계정도 보호 대상이 됨을 설명한다. 409는 최신 상태를 다시 불러오도록 안내한다. 서버는 버튼 상태에 의존하지 않는다.

## 10. 배포와 이전 절차

2026-10-20 현재 방침은 전체 기능 완성 후 하나의 릴리스다. 10.1은 Phase 1의 호환성 설계 기록이며 별도 운영 배포 지시가 아니다. 구현 중 관련 테스트·타입 검사를 수행하고, 최종 빌드·감사·전체 역할별 브라우저 검증은 통합 기능 완료 뒤 수행한다.

### 10.1 1단계 배포는 동작을 바꾸지 않는다

운영 배포가 마이그레이션을 같은 파이프라인에서 자동 적용하므로(2.2), 마이그레이션과 역할 조정과 코드 배포를 수동으로 나눌 수 없다. 대신 1단계가 권한의 실질을 바꾸지 않게 설계한다.

- 마이그레이션 `0008`이 기존 계정을 모두 `officer`, `approved`로 만들고 결정권은 주지 않는다. 지금 이 계정들이 가진 권한과 같으므로 배포 직후에도 세미나 글, 미디어, Q&A 답변을 그대로 쓸 수 있다.
- 새 코드가 배포되기 전 잠깐 동안 기존 Worker가 새 컬럼을 무시하지만, 추가만 하는 마이그레이션이므로 호환된다.
- 1단계에는 임원 전용 내용(임원 게시판), 승인 기능, 타인 글 숨김이 아직 없다. 그래서 임원 역할과 결정권 컬럼이 기존 권한 이상을 주지 않는다.

### 10.2 계정 명단 점검 (릴리스 gate 개방 전 필수)

배포 전에 계정 매핑·변경 SQL을 준비한다. 새 컬럼을 쓰는 실제 조정은 마이그레이션·코드 배포 후 릴리스 gate가 닫힌 상태에서 수행하고 재조회한다. 검증된 뒤 신규 기능을 연다.

1. 운영 D1의 계정 명단을 조회한다(`select username, display_name from users`). 이 명령은 읽기 전용이지만 운영 데이터를 읽으므로 사용자가 직접 실행하거나 명시적으로 승인한 뒤에 실행한다.
2. `src/data/members.json`의 직함과 대조한다. 현재 명단은 회장, 수석부회장, 이사 3명, 감사 1명, 수석고문 1명이다.
3. 감사·고문은 approved member로 조정하고 can_access_directors_forum = 1을 부여한다. 세미나·미디어·Q&A 공식 답변 권한은 제거하되 총회·임원 게시판과 공개 Q&A 질문을 이용한다. 이름이 확인되지 않은 계정은 자동 조정하지 않는다.
4. 표시 이름이 비어 있는 임원 계정은 이름을 채운다.
5. 회장과 부회장 계정에 결정권을 지정한다(`scripts/set-user-role.mjs`). 현재 회장과 수석부회장이 대상이다. 수석부회장도 결정권자라는 사용자 결정은 확정되었다. 공개 명단과 실제 계정을 대조한 뒤 bootstrap으로 지정한다.

### 10.3 스크립트 변경

- `scripts/create-user.mjs`는 새 기본값(`pending`) 때문에 그대로 두면 승인 대기 계정을 만든다. `--role officer|member`를 필수 인자로 받고 `status = approved`로 삽입하도록 바꾼다. 역할을 생략하면 오류로 끝나게 해서 의도하지 않은 권한 부여를 막는다. 결정권은 `--executive` 인자를 줄 때만 켜지고, `--role officer`와 함께일 때만 허용한다.
- `scripts/set-user-role.mjs`를 새로 추가한다. 역할(`officer`, `member`)과 결정권(`is_executive`)을 바꾼다. 결정권은 `officer`에게만 켤 수 있고, `member`로 바꾸면 결정권도 함께 끈다. 기존 `create-user.mjs`와 같은 방식으로 저장소 안의 `wrangler`를 직접 가리킨다.
- 해시 반복 횟수를 맞추는 `password-script-parity.test.ts`는 그대로 유지한다.

- 특별 접근 운영 스크립트 `set-user-forum-access.mjs`를 추가해 --allow/--revoke/--dry-run을 제공한다. 역할 변경 시 새 플래그를 일관되게 정리하고 revision을 증가시킨다. 사용자 관리 도입 후 운영 변경도 수행자·requestId·전후 권한 감사 기록을 남긴다.
- 신규 Forum·사용자 관리는 MEMBER_FEATURES_ENABLED가 정확히 true일 때만 연다. 초기값 false에서는 페이지/API 503과 메뉴 숨김으로 초기 계정 조정 중 노출을 방지한다. 초기 역할 검증 후 별도 운영 승인 범위에서 연다. 기존 기능에는 적용하지 않는다.
- 운영 변경·push·PR·merge·deploy는 사용자 승인 범위에서만 실행한다. 수동 운영 배포는 `TCN_CONTENT_SOURCE=remote npm run build && npx wrangler deploy`를 따른다.

## 11. 보안과 개인정보

- 신규 로그인 세션 기반 Forum·사용자 변경 API는 세션, 동일 출처, `sec-fetch-site`, 범위별 CSRF를 요구한다. 공개 signup은 세션 없이 별도 출처·입력·가입 플래그 검사로 처리한다. 기존 로그인·익명 Q&A의 방어와 Phase 1의 세미나·미디어 호환 정책을 유지한다.
- 로그인 속도 제한과 동일 응답 정책은 유지한다. 가입 코드 발송에는 이메일별(시간당 5회, 60초 간격)·IP별(시간당 10회) 속도 제한과 일일·월간 발송 예산을 두었고, 코드는 챌린지당 5회까지만 시도할 수 있다. 가입 코드와 재설정 링크 발송은 이에 앞서 Turnstile(`data-action` 이 각각 `signup_start`·`password_reset`)을 요구하며, 검증은 D1 을 쓰기 전에 끝난다.
- 이메일은 사용자 관리와 본인 계정 화면에만 필요한 범위로 표시한다. 공개 화면·Forum·로그·감사 기록에는 넣지 않는다. 이메일 형식이 아닌 기존 username을 이메일로 오표시하지 않는다.
- 개인정보 처리방침 페이지가 없으므로(`MEMBERSHIP_FLOW.md`) 통합 기능을 배포하더라도 `SIGNUP_ENABLED`를 켜기 전에 처리방침과 수집 항목, 보관 기간, 처리 책임자를 확정해야 한다.
- 비공개 글이 캐시나 검색 엔진에 남지 않도록 8.4의 헤더를 적용한다.
- 준회원은 이메일 소유 인증을 마친 뒤 승인 전에도 총회 게시판을 열람·작성한다. 승인은 총회 게시판 접근을 통제하지 못하므로, 가입을 공개하면 총회 게시판의 내용은 이메일 인증을 마친 누구에게나 열려 있다고 보아야 한다(16장).

## 16. 알려진 한계와 위험

- **이메일 인증의 한계:** 가입은 이메일 소유 인증을 마쳐야 완료되므로 다른 사람의 이메일로는 가입할 수 없다. 다만 인증은 메일함의 소유만 증명하고 신분은 증명하지 않는다. 결정권자가 이름과 소속으로 판단해야 한다.
- **준회원의 즉시 열람:** 승인은 총회 게시판 접근을 바꾸지 않는다. 이메일 인증을 마친 누구나 총회 게시판을 열람·작성할 수 있으므로, 승인 절차는 게시판 접근 통제로 작동하지 않는다. 가입이 꺼진 동안에는 노출되지 않는다.
- **계정 열거:** 최종 제출의 `email_taken` 응답은 코드를 인증한 이메일에만 나오고, 코드 발송 단계는 가입 여부와 무관하게 같은 응답을 준다. 그래서 다른 사람의 가입 여부를 알아내는 데는 쓸 수 없다.
- **비밀번호 규칙 통일:** 운영자 스크립트 `create-user.mjs`도 웹과 같은 규칙(NFC 정규화 후 15~64자, 제어·비가시 문자 거부, `isWeakPasswordShape`)을 쓰고 `pbkdf2-nfc`로 해시한다. `password-policy.test.ts`가 웹 `normalizeNewPassword`와의 결과 일치를 잠근다.
- **메일 발송 한도:** 가입과 재설정이 Resend Free의 한도(하루 90건, 월 2,900건을 예약)에 묶인다. 가입 코드는 하루 70건, 월 1,800건까지만 보내므로(재설정과 보안 알림 몫을 따로 둔다) 한도에 닿으면 가입이 일시적으로 막힌다. 같은 Resend 계정을 쓰는 다른 앱도 한도를 소모한다.
- **단독 승인:** 회장 또는 부회장 1명의 결정으로 회원이 되므로 정관의 이사회 의결과 다르다. 감사 기록으로 책임을 추적하고, 의결 자체는 사이트 밖의 조직 절차로 둔다.
- **가드 누락:** 커버리지 테스트는 호출 문자열을 확인할 뿐이다. 매트릭스 테스트와 핸들러 단위 테스트가 이를 보완한다.
- **임원 계정 점검 의존:** 감사·수석고문 계정이 임원으로 이전되는 위험은 10.2의 절차에 의존한다. 이 절차는 사람이 수행한다. 회장·부회장 결정권을 지정하지 않으면 가입 승인과 타인 글 숨김을 할 계정이 없다.

## 17. 검토 시 확인할 기본값

설계 승인 때 직접 다루지 않았고 명세서를 쓰면서 제가 정한 값이다. 바꾸고 싶으면 이 목록에서 지적한다. 10번부터는 2026-10-14 개정에서 추가한 값이다.

1. 비밀번호는 NFC 정규화 후 15~64자와 7.2의 약한 형태 거부, Pwned Passwords 검사를 적용한다. 이름은 1~100자, 소속은 200자 이하다.
2. 가입 직후 자동으로 로그인시키고 `/account`로 보낸다.
3. forum 목록과 사용자 관리 목록의 페이지 크기는 Q&A와 같은 20이다.
4. 로그인 후 기본 이동 경로는 임원 `/admin`, 준회원과 회원 `/forum/assembly`, 반려된 계정 `/account`다.
5. 표시 이름이 없는 계정은 "Officer" 또는 "Member"로 표시한다.
6. `SIGNUP_ENABLED`는 Workers 변수이고 값이 정확히 `true`일 때만 켜진다. 켜려면 설정 변경과 배포가 필요하다.
7. 비로그인 사용자의 "Sign in" 링크는 헤더가 아니라 푸터에 둔다. 로그인 상태에 따른 헤더 링크는 클라이언트 스크립트로 표시한다.
8. 감사 기록의 동작 이름은 `approved`, `rejected`, `reapproved`, `permissions_changed`다. 권한 부족 응답은 403 `forbidden`이다.
9. forum 본문은 일반 텍스트이고 자동 링크를 만들지 않는다.
10. 준회원도 총회 게시판에 글을 쓸 수 있다(열람만 허용하지 않는다).
11. 반려된 계정이 이전에 쓴 글은 그대로 남고, 결정권자가 글마다 숨긴다.
12. 상태 표시 이름은 `pending`이 "준회원", `approved` 회원이 "회원"이다. 화면 문구가 영어이므로 "Associate member"와 "Member"로 표시한다.
13. 결정권은 `users.is_executive` 플래그로 두고 `role` 값은 `officer`와 `member` 두 개로 유지한다.
14. (해결, 2026-10-21) 준회원이 이메일 인증 없이 총회 게시판을 열람하는 문제는 이메일 소유 인증을 가입 완료의 필수 선행 절차로 올려서 해결했다. 가입 공개 전에 남은 필수 조건은 개인정보 처리방침과 운영 메일 발송 설정이다(15장). 가입 경로의 봇 방어(Turnstile)는 2026-10-21에 구현했다.
