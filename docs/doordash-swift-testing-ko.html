Cursor와 Bazel로 XCTest를 Swift Testing으로 전환하기

DoorDash가 공유 iOS module의 test를 자동화 중심으로 이전하고 속도와 신뢰성을 함께 개선한 과정을 정리했다.

안내: 원문 전체 번역이 아닌 학습용 상세 요약이다. Swift, XCTest, Swift Testing, Cursor, SweetPad, MCP, Bazel 명칭은 영어를 유지했다.

전환 배경

DoorDash의 XCTest suite는 대부분 직렬 실행되어 CI의 test step이 두 자릿수 분까지 늘어났다. Swift Testing은 sync와 async test를 기본적으로 병렬 실행하고, #expect를 통해 실패 expression을 더 자세히 보여준다. 내부 benchmark에서는 test 실행 자체가 XCTest보다 4~7배 빠른 사례가 확인됐다.

세 가지 원칙

  1. Local ownership: 각 module team이 자기 test를 이전한다.
  2. Tooling first: 반복 가능한 규칙과 실행 환경을 먼저 만든다.
  3. Reliability gate: 빠른 실행과 test 신뢰성을 교환하지 않는다.

자동화 환경

SweetPad와 MCP

SweetPad는 VS Code와 Cursor에서 Xcode command-line tool을 이용해 Apple platform project를 build, test, debug하게 해준다. DoorDash iOS platform team은 SweetPad에 MCP server를 추가해 Cursor가 VS Code command를 호출하도록 했다. Agent는 source를 바꾼 뒤 같은 대화 흐름에서 target build와 test를 실행하고 실패를 다시 수정할 수 있었다.

Cursor migration rule

기계적 변환 규칙을 하나의 reusable rule로 만들었다. 주요 변환은 다음과 같다.

  • import XCTest → import Testing
  • XCTestCase → struct와 @Suite
  • XCTAssert* → #expect
  • XCTUnwrap → #require
  • XCTFail → Issue.record
  • expectation 기반 async test → confirmation, async iterator, continuation 기반 test
  • loop 기반 case → parameterized test

Rule은 의미를 새로 설계하는 도구가 아니라 반복 편집을 일관되게 수행하는 도구로 제한했다. 큰 test file은 먼저 책임별로 나눈 뒤 변환하도록 권장했다.

검증 loop

1. 한 test file을 변환한다.
2. 해당 package의 test를 실행한다.
3. compile error, crash, assertion failure를 수정한다.
4. 다시 실행한다.
5. package 전환 완료 후 10회 연속 통과를 확인한다.

초기에는 SweetPad MCP가 이 loop를 실행했다. Bazel 도입 후에는 prompt 자체에 bazel test <package> 명령과 반복 조건을 넣었다. Agent가 test command를 추측하지 않게 build system 사용법을 context로 제공한 점이 중요하다.

병렬 실행이 드러낸 flaky test

전환 후 발견된 flaky test 대부분은 Swift Testing이 새로 만든 문제가 아니었다. XCTest의 직렬 실행에 가려져 있던 shared mutable state, test order 의존, timing assumption이 병렬 실행으로 드러난 것이다.

  • 전역 cache나 singleton state를 test끼리 공유.
  • 앞 test가 값을 만들고 뒤 test가 암묵적으로 사용.
  • 고정 sleep이나 실행 순서에 의존하는 async assertion.
  • background thread에서 UIKit API를 호출하는 잘못된 test.

10회 연속 통과 조건은 이런 잠재 문제를 merge 전에 찾는 단순하고 강력한 gate가 됐다.

모든 test를 옮기지는 않음

assertMacroExpansion처럼 내부적으로 XCTest API에 의존하는 case는 남겼다. 목표는 migration 비율 100%가 아니라 더 빠르고 안정적인 suite다. ecosystem이 아직 지원하지 않는 test를 무리하게 바꾸지 않았다.

측정 결과

  • CI의 unit test step 약 60% 단축.
  • 공유 iOS package의 전체 build 평균 약 40% 단축.
  • 공유 module의 약 90%를 Swift Testing으로 이전.
  • 기존 suite가 잡던 regression coverage 유지.
  • CI 비용 절감과 주당 여러 engineer-day의 대기 시간 회수.
실무 적용: AI migration 성공 조건은 좋은 prompt 하나가 아니다. 명확한 mechanical rule, 실제 build/test tool 접근, package별 ownership, 반복 가능한 reliability gate, 전후 metric이 함께 있어야 한다.

읽으며 확인할 질문

  1. 우리 test suite에서 직렬 실행에 숨어 있는 shared state는 무엇인가?
  2. Agent가 수정 직후 실제 target test를 실행할 수 있는가?
  3. Migration 완료를 판단할 객관적인 반복 통과 조건이 있는가?
  4. 변환 전후 CI 시간, flake rate, 비용을 측정하고 있는가?
