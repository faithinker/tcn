DoorDash Engineering · Mobile

모바일 앱 크기를 줄이고 증가를 통제하는 방법

DoorDash와 Dasher 앱에서 사용한 분석, 최적화, 지속 감시 방법을 모바일 개발자 관점으로 정리한 한국어 상세 요약.

안내: 원문 전체 번역이 아닌 학습용 상세 요약이다. 기술명, 제품명, 회사명은 원문 표기를 유지했다.

핵심 문제

기능과 팀이 늘면 모바일 바이너리도 자연스럽게 커진다. 문제는 개별 변경의 증가량이 작아 보여도 장기간 누적되면 설치 전환율, 업데이트 속도, 저장 공간, 저사양 기기 성능에 영향을 준다는 점이다. DoorDash는 특히 App Store의 셀룰러 다운로드 경고가 나타나는 크기에 가까워지는 추세를 위험 신호로 봤다.

크기를 키우던 주요 원인

  • 이미지와 번들 자산: 중복 이미지, 필요 이상으로 큰 해상도, 비효율적인 포맷.
  • Build configuration: 최적화가 제대로 적용되지 않거나 배포 바이너리에 불필요한 코드와 symbol이 포함되는 설정.
  • Dependency: 쓰이지 않거나 중복된 third-party library와 기능 대비 무거운 SDK.

실행한 최적화

1. Asset 전수 조사

모든 bundled image를 조사해 중복과 대형 자산을 찾았다. 로컬 번들에 반드시 있어야 하는지 검토하고, 적절한 경우 네트워크 전달로 전환했다. 다만 네트워크 자산은 첫 화면 지연이나 오프라인 경험을 해치지 않는 범위에서만 사용했다.

2. Build 결과 비교

소스 코드 줄 수만 보지 않고 실제 배포 산출물을 비교했다. 두 빌드의 binary diff를 통해 어떤 framework, symbol, asset이 증가분을 만들었는지 추적했다. 이 방식은 “이번 PR이 왜 커졌는가”를 구체적인 항목으로 바꿔준다.

3. Dependency 정리

동일 기능을 제공하는 여러 library, 사용하지 않는 module, 큰 비용을 요구하는 SDK를 검토했다. 제거 가능 여부뿐 아니라 더 작은 구현이나 동적 전달 방식으로 대체할 수 있는지도 판단했다.

재발 방지 장치

  • Release-over-release report: 매주 release candidate와 현재 production 앱 크기를 자동 비교해 모바일 엔지니어링 Slack channel에 게시.
  • Main branch monitoring: main에 merge될 때마다 직전 build와 비교. 임계값을 넘으면 즉시 alert.
  • PR approval group: 새 asset을 추가하는 PR은 전담 reviewer가 포맷, 해상도, 압축, 번들 포함 필요성을 확인.
  • 감소도 기록: 크기가 줄어든 변경도 알려 좋은 최적화 패턴을 다른 팀이 재사용하도록 함.

결과와 의미

DoorDash는 두 앱의 크기를 각각 약 7% 줄이고, 이후 증가를 조기에 발견할 수 있는 운영 체계를 만들었다. 중요한 성과는 일회성 다이어트보다 모든 추가 MB가 의도된 비용인지 지속적으로 검증하는 구조다.

실무 적용: 앱 크기를 release 직전 품질 지표가 아니라 PR 단계의 product metric으로 취급한다. 먼저 production IPA/APK/AAB 기준선을 만들고, main build diff와 임계값 alert부터 자동화하면 효과가 크다.

읽으며 확인할 질문

  1. 우리 앱에서 asset, executable, framework 중 가장 빠르게 증가하는 영역은 어디인가?
  2. PR 작성자가 binary size delta를 merge 전에 볼 수 있는가?
  3. 네트워크 전달로 바꿀 자산과 반드시 번들에 남길 자산의 기준이 있는가?
  4. 앱 크기 감소가 install conversion과 저사양 기기 경험에 미친 영향을 측정하는가?
