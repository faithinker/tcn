08구조상 관측

의존성 그래프에서 읽히는 것들입니다. 09 의 개선 작업이 반영된 뒤 상태 기준입니다.

런타임 계층 역행이 0 이 되었습니다

268개 내부 엣지 중 계층을 거스르는 것은 이제 하나뿐이고, 그것마저 data/organization-milestones.ts → lib/seminars 의 import type 이라 빌드 시 소거됩니다. 유일했던 런타임 역행 components/seminars/CommunityPost.astro → layouts/BaseLayout 은 파일이 layouts/SeminarPostLayout.astro 로 옮겨가면서 사라졌습니다. 순환 의존은 없습니다.

바인딩 접근이 한 파일로 좁혀져 있습니다

D1·R2·ASSETS 접근이 전부 lib/db/client.ts 를 거칩니다. 48개 테스트가 바인딩 목킹 없이 도는 이유이자, 라우트 계약 테스트 10개를 lib/routes/ 에 소스 없이 테스트만 두고 운영할 수 있는 이유입니다.

lib/qna 는 836줄로 여전히 도메인 중 가장 무겁습니다

security.ts 하나가 CSRF 토큰, 동일 출처 검사, rate limit, Turnstile 검증을 안고 있습니다. 소스를 열어보니 무게의 일부는 관심사가 뭉친 것이 아니라 아래 계층에 공용 crypto 가 없어서 각자 만든 것이었고, 그건 lib/crypto 를 새로 두면서 해소됐습니다(09-02). 남은 무게는 rate limiter 중복(09-04)이며 아직 미적용입니다.

components/admin 이 내부 결합 21로 가장 조밀합니다

13개 파일 1,669줄이 서로를 21번 참조합니다. 다만 PostEditor.tsx 가 5개 하위 컴포넌트를 조립하는 허브이고 상태 로직은 readiness · publish-state · pending-media · media-order 순수 함수로 빠져 있어, 조밀함이 곧 얽힘은 아닙니다.

i18n 이 프레젠테이션 전용으로 고립돼 있습니다

i18n 은 33번 import 되지만 자신은 lib 어느 모듈도 부르지 않습니다. 본문 원문 554줄이 i18n/content.ts 에 있는데, 도메인 로직이 이걸 읽지 않으므로 번역 작업이 비즈니스 로직을 건드릴 일이 없습니다.

09개선 제안

08 의 관측을 소스까지 따라가서 확인한 것들입니다. 그래프에서는 안 보이던 중복이 대부분이고, 위험 대비 효과 순으로 정렬했습니다. 01·02·03·06 과 05 의 절반이 적용됐습니다. 적용 후 vitest 48파일 335건 전부 통과, astro check 179파일 0 에러를 확인했습니다. 근거에 적힌 줄 번호는 개선 전 기준입니다.

01

같은 파일 안에서 복붙된 출처 검증

적용 완료 risk 없음 6줄 → 1줄
근거
src/lib/qna/security.ts:63-68 requireAdminMutation 안의 인라인 검사
src/lib/qna/security.ts:80-88 requireSameOrigin, 글자 단위로 동일

origin 일치 검사와 sec-fetch-site cross-site 차단이 같은 파일 안에서 두 번 쓰였습니다. 아래 함수를 호출하면 끝입니다. 

-  const expectedOrigin = new URL(request.url).origin;
-  const origin = request.headers.get('origin');
-  if (!origin || origin !== expectedOrigin) throw new QnaSecurityError('invalid_origin', 403);
-
-  const fetchSite = request.headers.get('sec-fetch-site');
-  if (fetchSite === 'cross-site') throw new QnaSecurityError('cross_site_request', 403);
+  requireSameOrigin(request);

결과: security.ts:49 에 반영됨. 함수 선언은 호이스팅되므로 정의보다 앞서 호출해도 문제없습니다.

02

crypto 헬퍼 3중복을 lib/crypto 로 승격

적용 완료 risk 낮음 경계 침범도 함께 해소
근거
lib/auth/session.ts:11-21 · lib/qna/security.ts:22-33 HMAC-SHA256. as BufferSource 캐스트까지 동일
lib/auth/rate-limit.ts:10-14 · lib/qna/security.ts:35-38 SHA-256. 출력만 hex vs base64url

08 에서 lib/qna 가 관심사를 뭉쳐 안고 있다고 읽었지만 실제 원인은 아래 계층에 공용 crypto 가 없어서 두 도메인이 각자 만든 것이었습니다. lib/auth/_crypto.ts 를 lib/crypto/ 로 올리고 hmacSha256 · sha256 을 얹으면 3벌이 사라집니다.

덤으로 경계 침범이 해소됩니다. _ 접두사는 lib/auth 내부용이라는 표시이고 auth/index.ts 가 재수출하지 않는데, lib/qna 가 그 공개 표면을 건너뛰고 직접 가져다 쓰고 있습니다.

결과: lib/crypto/index.ts 신설(58줄), lib/auth/_crypto.ts 삭제. hmacSha256 · sha256 · bytesToHex 로 3벌이 1벌이 됐고 lib/auth 는 296줄에서 252줄로 줄었습니다. 02 계층도에 lib/crypto 노드가 새로 생겼습니다.

03

클라이언트 IP 추출을 하나로

적용 완료 보안 판단 필요 현재는 잠복
근거
lib/auth/rate-limit.ts:21-24 cf-connecting-ip ?? x-forwarded-for[0] ?? unknown
lib/qna/security.ts:92 cf-connecting-ip ?? unknown

x-forwarded-for 는 클라이언트가 조작할 수 있는 헤더입니다. 이걸 rate limit 버킷 키로 쓰면 헤더를 돌려가며 IP 제한을 우회할 수 있습니다.

Workers 에서는 cf-connecting-ip 가 항상 채워지므로 지금은 도달하지 않는 폴백입니다. 다만 다른 프록시 뒤나 테스트 하니스에서 돌면 살아납니다. auth 쪽 폴백을 없애 qna 와 맞추는 쪽을 권합니다.

결과: x-forwarded-for 폴백 제거. 다만 이 변경과 함께 들어온 import 문이 rate-limit.ts 파일 맨 아래에 붙어 있어 상단으로 옮겼습니다. ES 모듈 import 는 호이스팅되므로 동작에는 영향이 없었지만 의도한 코드가 아닙니다.
